Relay × Agent Harness · 定位对比与差异分析

对照标尺：业界通用义「agent harness」（模型之外的运行时与控制层）· 项目路径 D:\Tools\qianwen\relay-glue

结论速览

① 两者不是竞品，是上下游

  • harness 管「一个 agent 内部怎么跑」：模型循环、上下文装配、工具执行、权限、停止条件。
  • Relay（relay-glue） 管「多个 agent 之间怎么交接、怎么被管」：契约、闸门、记账、分诊、回放。
  • Relay 自己不调模型（server/ 内零 anthropic/openai/api key，已核），它是编排域的 harness，位于各 worker 自带 harness 的上游/旁路。

② 五支柱覆盖：3 根自建 · 2 根外包

  • 本项目实现 Loop Discipline（显式重试/续跑/停链/预算停）
  • 本项目实现 Policy Enforcement（三档安全闸门 + 人工确认）
  • 本项目实现 Context Lifecycle（黑板状态 + 交接契约校验）
  • 外包给 worker Context Assembly（worker 自己的上下文）
  • 部分覆盖 Tool Integrity（跨应用靠适配器 + 分诊兜底）

③ 最大的结构性缺口

  • 元宝没有 harness（纯 GUI），它是整条链里唯一「无运行时护栏」的环节 → 只能靠 ensureInput() 自愈 + 安全闸门兜底。
  • 模型驱动的反思重规划仍未实现（补强①已让模型能改链，但还做不到 harness 那种自由决策下一步）。

④ 选型一句话

  • 想把一个 agent 跑好 → 用 harness。
  • 想把几个已在跑的 agent 拼成一条可信、可管、可查账的流水线 → 用本项目。
  • 现实分工：WorkBuddy / CodeBuddy 各自是 harness，Relay 是它们之间的胶水 + 治理面。

一、标尺：业界说的「agent harness」是什么

来源定义要点
Microsoft Agent Framework 文档harness 是把语言模型变成能干活 agent 的运行时脚手架：驱动模型与工具调用、管理会话状态与上下文、施加审批策略、让 agent 在多步任务中持续推进。典型能力：函数调用（含每次请求的迭代上限）、历史持久化、上下文压缩、Todo/计划跟踪、工具审批与自动审批规则、可观测性、后台子智能体、Shell 执行、有界循环。
社区「五支柱」框架① Context Assembly 上下文装配　② Tool Integrity 工具完整性（调用前 schema 校验 + 可行动错误）　③ Loop Discipline 循环纪律（显式 continue/retry/halt 信号，而非启发式）　④ Policy Enforcement 策略执行（每次调用过权限门）　⑤ Context Lifecycle 上下文生命周期（上下文当作有限、可枯竭的资源主动管理）。
中文工程系列（业界共识）AI Harness = 围绕模型、上下文、工具与 Agent Loop 搭建的运行与控制层：上下文管理 / 任务循环 / 工具管理 / 任务状态 / 权限控制 / 沙箱 / 重试恢复 / 日志追踪 / 人工确认。并强调硬停止条件：max_steps、max_retries、timeout、token_budget、cost_budget、explicit_finish、fatal_error。
标尺要点：harness 的本质是「模型之外那层让 AI 系统可靠、可控、可恢复的运行时」；判断一个系统是否 harness，看它有没有上下文装配 / 工具校验 / 循环纪律 / 权限门 / 硬停止这五件事。

关键读法：系统里有两层 loop。外层是 WorkBuddy 的 harness loop（模型决定调不调、调用哪个工具）；内层是 Relay 的 pipeline loop（规则决定链内下一步交给谁）。Relay 不替代 harness，它替 harness 管住跨应用的那一段。

五、结构性优势与结构性短板

优势（harness 给不了的）

  • 交接不丢：契约 + 校验器，专治「A 查的 B 视而不见」。
  • 跨形态统一：CLI 型（CodeBuddy）、GUI 型（元宝/VSCode）、harness 型（WorkBuddy）同一套契约。
  • 失败可诊断：分诊表把第三方怪癖（端口占用、选择器漂移、CLI 未登录）翻译成人能修的提示。
  • 成本可见：按项目/按日分账，超预算自动降级回单 agent（多 agent 成本是生死线）。
  • 可回放可审计：每步 worker/耗时/成本/产物都在盘上，事后能查、能重跑。
  • 不被上游打断：零框架依赖，SDK 升级不炸。

短板（harness 天生有的）

  • 没有反思重规划：链是阶段化的，模型能改链（补强①已通）但还不能像 harness 那样在每轮之间自由决定下一步动作。
  • 成本是估算：不持模型就拿不到真实 token，只能按字符估。部分已改善：CodeBuddy 腿已取到 CLI 真实 usage；元宝（GUI 无 API）仍是估算。
  • 延迟高：落盘 + 跨进程等待，不适合高频对话型 agent。
  • 边界处理全靠自己：CDP --remote-allow-origins=*、-p --max-turns 1 --tools ""、--port 自动重选、元宝 ensureInput() 自愈——这些在成熟 harness 里都是现成的。
  • 最弱一环无护栏：元宝没有 harness，纯 GUI 自动化，天然最脆。
  • 生态为零：没有第三方工具、评测、trace 集成。

结论变化：补强 ① 落地后，Relay 在「编排域」已具备 harness 的关键能力——模型能自己决定下一步跑什么；它与通用 harness 的剩余差距，主要是「模型驱动的动态 loop（反思重规划）」与「上下文压缩策略」这两项深度能力，而不是能力有无问题。

七、一句话总结

harness 让一个模型变成能可靠干活的 agent；Relay 让几个已经在干活的 agent 变成一条可交接、可审批、可查账、可回放的流水线。
两者不是替代关系——现实分工是 WorkBuddy / CodeBuddy 各自当 harness，Relay 当它们之间的胶水与治理面。补强①落地后 Relay 已能在编排域自己改链、自己回滚；下一步真正值得追的，是 harness 那种模型驱动的动态 loop（反思重规划），以及把上下文压缩策略做深。
